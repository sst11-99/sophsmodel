### Roll back safely

Yes: “go back to Git version 1” is a meaningful request using the checkpoint above. It requires an explicit code restoration and a website deployment. Merely viewing the old GitHub branch does not change the live site.

1. Check the current branch, working-tree changes and live deployment. Preserve uncommitted work. Read changes made after Version 2 before deciding whether a full rollback or a narrow UI revert is appropriate.
2. Compare `version-1` and `version-2`. To undo only this release, create a new revert commit for the Version 2 release commit. This preserves history and retains the Version 1 repeat-submission guard. Do not force-push or reset shared `main` backwards.
3. Run the regression tests and preview both phone and desktop layouts. If reverting asset references could reuse a cached file, use fresh cache versions in the rollback release.
4. Push the verified rollback through GitHub MCP and deploy it to Vercel. If a verified Vercel deployment of Version 1 exists, it can instead be promoted through the normal deployment workflow; first confirm its source and configuration match the intended checkpoint.
5. Verify the production domain's actual scripts/styles and behavior. Record the rollback commit and deployment IDs here. Keep Version 2 available for comparison or reapplication.

### GitHub versus the live website

A successful GitHub push means the code is saved remotely. It does not by itself prove a Vercel production deployment happened. Earlier releases used explicit file-list deployments, so verify whether Git integration is configured before relying on automatic builds. Deploy only serving files: HTML/CSS/browser scripts, the locale endpoint, required images and font. Keep tests, scripts, release/audit documents, database migrations and private records out of the public serving bundle. `.vercelignore` is a secondary safeguard, not proof that an arbitrary API deployment's file list is safe.
